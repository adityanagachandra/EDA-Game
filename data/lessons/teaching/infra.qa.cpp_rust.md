# C++ and Rust in EDA

Almost every production EDA engine, commercial or open source, has a C++ core: OpenROAD, OpenSTA, Yosys, KLayout, Verilator and Xyce among them. The choice is not fashion. Engines touch hundreds of millions of objects in tight loops and need control of memory layout and native speed. C++ also brings use-after-free bugs, data races and a fragile binary interface. Rust is increasingly used for new components because it removes whole classes of these bugs at compile time, and real tools increasingly mix the two, which makes the boundary between languages a design problem.

## Why EDA cores are written in C++

Three properties keep C++ at the core. Performance: compiled native code, templates that the compiler instantiates and inlines per type, and no interpreter or garbage collector between the algorithm and memory. Layout control: the engineer decides whether instances live in arrays of structures or structures of arrays, uses 32-bit ids instead of 64-bit pointers, and pools allocations, which decides cache behaviour on large designs. Ecosystem: decades of EDA code, libraries and expertise.

The costs are equally concrete. Manual memory management produces dangling pointers, for example a stale pointer to an instance that an optimizer deleted. The C++ ABI, including name mangling, class layout and standard-library internals, differs between compilers and versions, so a plug-in built with one toolchain can crash when it receives a std::string from another. Long compile times come from heavy headers and templates. Large EDA code bases control these risks with handle-based object access, sanitizers in CI and narrow C-style plug-in boundaries.

## What Rust's ownership buys

Rust's ownership rules say that every value has one owner, and that at any moment there is either any number of shared references to it or exactly one mutable reference. The compiler enforces this, so safe Rust code cannot use freed memory and cannot have data races: a router that shares a read-only grid among threads and gives each thread exclusive mutable access to its own region compiles, while one in which two threads could write the same cell does not.

Rust does not make an engine deterministic: floating-point reductions in timing-dependent order still vary, which remains the programmer's job. And single ownership fits cyclic pointer graphs badly; a netlist where nets point to pins and pins point back to nets is awkward with references. Rust EDA code therefore usually stores objects in arenas or vectors and refers to them by integer index, the same id-based pattern good C++ databases use, which also happens to be cache friendly.

## Crossing language boundaries

Real tools mix languages: a C++ core, Tcl and Python for scripting, and increasingly Rust components. Every boundary needs a contract. OpenROAD exposes its C++ engines to Tcl and Python through wrappers generated by SWIG, glue code that converts arguments and wraps native objects in script handles. A script that keeps a handle to an instance the engine has since deleted can crash or read garbage unless the binding checks validity, so ownership across the boundary must be designed, for instance by passing ids that are checked on use.

Between Rust and C++, the robust interface is the C ABI: plain structs, explicit create and destroy functions, and no language-specific types such as std::vector or Vec crossing the line. Memory-safety guarantees stop at that boundary; the unsafe wrapper code must uphold lifetimes and aliasing by hand. A rule of thumb for new components: hot per-object loops in C++ or Rust, orchestration and report post-processing in Python.
